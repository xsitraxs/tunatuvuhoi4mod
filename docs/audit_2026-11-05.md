### Главный вердикт

**Требует точечных доработок.** Это качественный, хорошо задокументированный мод без крэшей и потери данных в основных сценариях. Однако релиз 1.1.5 помечен версией в дескрипторах, **не пройдя внутриигровой прогон** (README честно это фиксирует), а в новой военной ветке стоит имя оборудования, которое либо сломает выдачу наград, либо указывает на то, что старые фокусы выдают технику по несуществующему имени — одно из двух. До публикации 1.1.5 обязателен один короткий игровой прогон по error.log и точечные правки из Этапа 1.

### Топ-3 самых опасных риска прямо сейчас

1. **[S-1] Имена техники в новой ветке** (`infantry_equipment_0`, `support_equipment_1` в `TT_war_border_depots`/`TT_war_red_army_salvage`) противоречат `infantry_equipment` из старых фокусов. Прецедент 1.1.3 («invalid database object: tac_bomber_equipment») показывает, что такой баг даёт **молчаливый пропуск наград + спам в error.log**. Тест «supported names» подтверждает только самосогласованность, не БД движка.
2. **[A-1] Тупик послевоенной главы**: `TT_masters_of_siberia` выдаётся **только** успешным Тайшетским договором (`tt_tuva.10`), а `TT_postwar_ready`, категория `TT_postwar_category` и финал дерева `TT_war_new_siberian_border` от него зависят. Если СССР исчезнет иным путём (полная аннексия Тувой/союзником, коллапс), 7 решений, 6 событий, финал дерева и суперсобытие навсегда недоступны **без единого сообщения игроку**.
3. **[Q-1/Q-2/S-1] Незакрытая валидация движком**: хан-лидер создаётся через loc-ключ `TT_khan_leader_name` — тот же паттерн, который в 1.1.4 показывал ключи буквально у командиров; синтаксис `cancel = { ... }` в трёх фокусах не сверён с документацией движка; текущая версия не прогонялась в игре. Один 30-минутный прогон закрывает все три пункта.

### Сильные стороны

- **Идемпотентность и сейв-безопасность как паттерн**: повторная проверка всех условий в момент ответа (`TT_taishet_response_valid`), timed-флаги (`set_country_flag = { flag = ... days = N }`), `fire_only_once` + собственные флаги-предохранители, награды только после фактической передачи регионов (`TT_taishet_settlement_transferred` → `white_peace`).
- **Совместимость**: ни один ванильный файл не перезаписывается (косметика — в отдельном `tt_tuva_cosmetic.txt`), все идентификаторы под префиксами `TT_`/`tt_tuva`/`tt_postwar`, `on_actions` аддитивные, Scripted GUI не трогает чужие интерфейсы.
- **Документация уровня дизайн-дока**: `docs/taishet_campaign.md`, `postwar_siberia.md`, `taishet_superevent.md`, `kilo_khozhuun_handover.md` содержат обоснования решений, честные ограничения («с установленной HOI4 1.19.4 не сверено») и ручные тест-планы.
- **Тестовая модель** `tests/war_focuses.test.js`: мини-парсер Clausewitz + интерпретатор триггеров + 28 структурных проверок (циклы зависимостей, коллизии координат, инварианты наград, паритет локализации с BOM).
- **Локализация**: 392/392 ключа RU/EN, одинаковый порядок, UTF-8 BOM + LF, сбалансированные `§Y…§!`-теги (проверено автоматически).
- **Производительность**: `on_daily_TAN`/`on_daily_SOV` вместо глобальных циклов; `every_state`/`any_state` выполняются только в момент дипломатического ответа.

## 2. Детальный разбор проблем (по блокам)

### Блок 1. Архитектура и проектирование

#### [A-1 · 🟠 High] Послевоенная глава недостижима без Тайшетского договора — тихая потеря контента

- **Локация:** `common/scripted_triggers/tt_tuva_postwar.txt` (`TT_postwar_ready`), `common/decisions/tt_tuva_postwar.txt`, `common/decisions/categories/tt_tuva_postwar_categories.txt` (`visible = { has_idea = TT_masters_of_siberia }`), `common/national_focus/tt_tuva_focus.txt` (`TT_war_new_siberian_border`), `events/tt_tuva_events.txt` (`tt_tuva.10` — единственное место выдачи духа).
- **Описание проблемы.** Дух `TT_masters_of_siberia` выдаётся исключительно в `tt_tuva.10` (option A успешного договора):
  ```
  swap_ideas = { remove_idea = TT_siberian_gambit add_idea = TT_masters_of_siberia }
  ```
  При этом `TT_postwar_ready` требует `has_idea = TT_masters_of_siberia` **и** `TT_owns_taishet_package = yes`, а решение `TT_dictate_peace_in_siberia` видно только при `country_exists = SOV`. Если СССР прекращает существовать без договора (полная аннексия Тувой, раздел в мирной конференции с союзником, коллапс на другие теги), договор оформить нечем, дух не выдаётся, и навсегда закрываются: категория «Сибирский совет» (7 решений), 6 событий `tt_postwar.*`, суперсобытие (`TT_open_taishet_superevent` требует дух) и финал дерева `TT_war_new_siberian_border`.
- **Impact (риски).** Игрок, который *больше* завоевал (взял всю Сибирь силой), получает *меньше* контента, чем по договору, и не видит причины. Для мода с заявленной «послевоенной главой» это потеря ~20% контента в валидном альтернативном сценарии; для ИИ-Тувы в неисторичке — вероятный сценарий.
- **Решение (Before / After).** Добавить фолбэк-решение по образцу `TT_proclaim_manchurian_victory` (в файл `common/decisions/tt_tuva_postwar.txt`):

  ```txt
  # Before: единственный путь к послевоенной главе — tt_tuva.10 (договор),
  # а при исчезновении SOV решение TT_dictate_peace_in_siberia исчезает.

  # After: фолбэк «Провозгласить сибирскую победу»
  TT_proclaim_siberian_victory = {
      icon = GFX_decision_generic_nationalism
      cost = 0
      fire_only_once = yes
      allowed = { original_tag = TAN }
      visible = {
          has_completed_focus = TT_the_siberian_gambit
          NOT = { has_idea = TT_masters_of_siberia }
          NOT = { country_exists = SOV }
      }
      highlight_states = { highlight_state_targets = { state = 40 state = 654 state = 563 state = 564 state = 565
          state = 566 state = 567 state = 568 state = 569 state = 570 state = 574 state = 575 state = 576 state = 578 } }
      available = {
          custom_trigger_tooltip = { tooltip = TT_taishet_package_uncontested_tt TT_owns_taishet_package = yes }
      }
      complete_effect = {
          if = {
              limit = { has_idea = TT_siberian_gambit }
              swap_ideas = { remove_idea = TT_siberian_gambit add_idea = TT_masters_of_siberia }
          }
          else = { add_ideas = TT_masters_of_siberia }
          add_political_power = 150
          add_stability = 0.10
          TT_queue_taishet_superevent = yes
          TT_postwar_queue_reactions = yes
      }
  }
  ```
  И/или расширить `TT_postwar_ready` веткой `OR` (дух договора **или** владение пакетом при несуществующем СССР). Сценарий «мир без договора» обязан иметь точку входа в послевоенную главу — симметрично маньчжурскому финалу.

#### [A-2 · 🟡 Medium] Асимметрия восстановления pending-флагов: тайшетский чинится, коридор и мандат — нет

- **Локация:** `common/scripted_effects/tt_tuva_siberian_campaign.txt` (`TT_cleanup_taishet_pending`), `common/on_actions/tt_tuva_siberian_campaign.txt` (`on_daily_TAN`), `common/scripted_triggers/tt_tuva_scripted_triggers.txt` (`TT_can_request_siberian_corridor`, `TT_can_request_war_mandate`), `common/decisions/tt_tuva_decisions.txt` (`TT_request_siberian_corridor`, `TT_request_war_mandate`).
- **Описание проблемы.** Для Тайшетского запроса есть ежедневная зачистка висящего флага (`TT_cleanup_taishet_pending` снимает `TT_taishet_request_pending`, если войны с СССР больше нет). Для `TT_corridor_request_pending` и `TT_war_mandate_pending` такой зачистки нет — они снимаются только опциями событий `tt_tuva.17`/`tt_tuva.20`. Если событие потеряно (СССР исчез в день доставки `days = 1`, другой мод, консоль), флаг остаётся навсегда, и решения «Запросить сибирский коридор»/«Согласовать самостоятельные военные действия» блокируются тултипом «нет ожидающего запроса» без пути разблокировки. README признаёт это («автоматического таймера восстановления нет»), но для коридора/мандата проблема решается тривиально и безопасно.
- **Impact.** Потеря доступа к 2 дипломатическим решениям и их новостям в этом сохранении; игрок не понимает, почему решение «недоступно, хотя условий нет».
- **Решение (Before / After).** Добавить в `TT_cleanup_taishet_pending`-стиле узкую, безопасную зачистку (событие, адресованное несуществующей стране, гарантированно не придёт, поэтому «опоздавший ответ» невозможен в принципе):

  ```txt
  # Before: TT_cleanup_taishet_pending чинит только TT_taishet_request_pending

  # After: общий cleanup в on_daily_TAN
  TT_cleanup_diplomatic_pending = {
      if = {
          limit = { has_country_flag = TT_taishet_request_pending NOT = { has_war_with = SOV } }
          clr_country_flag = TT_taishet_request_pending
      }
      # Событие tt_tuva.17/tt_tuva.20 адресовано SOV: при несуществующем SOV оно
      # утеряно движком и никогда не сможет «съесть» более новый запрос.
      if = {
          limit = { has_country_flag = TT_corridor_request_pending NOT = { country_exists = SOV } }
          clr_country_flag = TT_corridor_request_pending
      }
      if = {
          limit = { has_country_flag = TT_war_mandate_pending NOT = { country_exists = SOV } }
          clr_country_flag = TT_war_mandate_pending
      }
  }
  ```
  Намеренно **не** добавлять таймер-истечение: инвариант «старый ответ не потребляет более новый запрос» (см. README) должен сохраниться; зачистка только по несуществованию адресата его не нарушает.

#### [A-3 · 🟡 Medium] «Манифест» из 14 регионов продублирован в 4 местах скрипта + 1 в тесте

- **Локация:** список `40, 654, 563–570, 574–576, 578` повторён в: `common/scripted_triggers/tt_tuva_siberian_campaign.txt` (`TT_taishet_package_uncontested`, `TT_owns_taishet_package`), `common/scripted_effects/tt_tuva_siberian_campaign.txt` (`TT_transfer_taishet_package`), `common/decisions/tt_tuva_decisions.txt` (`highlight_states` решения `TT_dictate_peace_in_siberia`), `tests/war_focuses.test.js` (`packageIds`) и `docs/taishet_campaign.md` (таблица).
- **Описание проблемы.** Это осознанный компромисс (в Clausewitz нет массивов), но любое изменение пакета требует синхронной правки пяти мест. Тест сегодня косвенно ловит расхождение списка `TT_owns_taishet_package` (тест «Finale blocks every missing treaty state»), но **не** ловит расхождение `TT_transfer_taishet_package` и `TT_taishet_package_uncontested` — их списки разобраны тестом только частично (файл эффектов парсится лишь на `remove_ideas`/`add_timed_idea`).
- **Impact.** Ошибка синхронизации при следующем изменении договора передаст игроку «гарантированный пакет» с дырой (например, регион из `uncontested`, но не из `transfer` — мир без региона, и наоборот: регион из transfer украсть у третьей страны, что противоречит документированной гарантии).

### Блок 2. Качество кода и технический долг

#### [Q-1 · 🟡 Medium] Хан-лидер создаётся с loc-ключом — риск повторения бага класса 1.1.4

- **Локация:** `common/national_focus/tt_tuva_focus.txt`, фокус `TT_the_second_khanate`:
  ```txt
  create_country_leader = {
      name = TT_khan_leader_name        # <-- без кавычек: loc-ключ
      desc = "TT_khan_leader_desc"
      ...
  ```
- **Описание проблемы.** Чейнджлог 1.1.4 фиксирует подтверждённый движком баг: «legacy-эффекты создания командиров показывали ключи локализации буквально» — для `create_corps_commander`/`create_field_marshal` автор перешёл на явные строки (`name = "Соян Чооду"`). Хан создаётся соседним эффектом `create_country_leader` и **остался на loc-ключе** (`TT_khan_leader_name: "Алдын-оол Хан"` / `"Aldyn-ool Khan"`). Если `create_country_leader` разрешает имена так же, как эффекты командиров, игрок увидит лидера по имени «TT_khan_leader_name». Прямого доказательства нет (не проверено в игре), но паттерн идентичен доказанному багу.
- **Impact.** Видимый всем игрокам национального пути дефект UI; антитеза заявленному «именной хан-лидер».
- **Решение (Before / After).** Проверить в игре за 2 минуты (фокус через консоль `focus.autocomplete`); при буквальном показе — свернуть к литералу, как у командиров, либо (лучше для RU/EN) оставить loc-ключ и создавать лидера механизмом, гарантированно читающим локализацию:

  ```txt
  # Before
  name = TT_khan_leader_name

  # After (минимальный, симметричный решению 1.1.4 для командиров)
  name = "Aldyn-ool Khan"
  ```
  Зафиксировать результат проверки в README (раздел «Совместимость и ограничения» уже описывает создание лидера — добавить туда же строку о том, как разрешается имя).

#### [Q-2 · 🟡 Medium] Ключ `cancel = { ... }` в фокусах не сверён с движком — тест моделирует поведение, которого в игре может не быть

- **Локация:** `common/national_focus/tt_tuva_focus.txt`, фокусы `TT_war_transsib_advance`, `TT_war_red_army_salvage`, `TT_war_taishet_junction`:
  ```txt
  cancel_if_invalid = no
  continue_if_invalid = yes
  cancel = { NOT = { TT_siberian_campaign_active = yes } }
  ```
- **Описание проблемы.** Документация HOI4 по фокусам фиксирует `cancel_if_invalid`/`continue_if_invalid`, но ключ `cancel` в стандартном наборе атрибутов фокуса не подтверждён. Тест «Running milestones survive loss but not peace» интерпретирует `cancel` в своей модели и доказывает задуманную семантику «проект переживает потерю узлов, но отменяется при мире» — однако при неподдерживаемом ключе движок проигнорирует блок (сообщение в error.log), и фокусы будут **не** отменяться при мире (награды всё равно защищены guard'ом `TT_siberian_campaign_active`, так что ущерб ограничен UX и потраченным временем фокуса).
- **Impact.** Расхождение модели и движка; при мире посреди 21-дневного проекта фокус продолжится и выдаст… ничего (guard награды сработает) — «пустой» фокус вместо отмены.
- **Решение (Before / After).** Пункт ручного тест-плана (см. §5): форсировать мир (`white_peace` из консоли) на середине `TT_war_transsib_advance` и проверить отмену фокуса + свежий error.log. Если ключ не поддерживается:

  ```txt
  # Before
  cancel_if_invalid = no
  continue_if_invalid = yes
  cancel = { NOT = { TT_siberian_campaign_active = yes } }

  # After (если cancel не поддерживается): смириться с cancel_if_invalid = yes
  # (проект отменяется и при потере узлов — терпимо, награды защищены), либо
  # перенести семантику в available-гвард + документированное поведение.
  ```

### Блок 4. Стабильность, совместимость, безопасность ассетов (AppSec-аналог)

#### [S-1 · 🟠 High] Противоречие имён оборудования: `infantry_equipment_0`/`support_equipment_1` (новая ветка) vs `infantry_equipment` (старые фокусы)

- **Локация:** `common/national_focus/tt_tuva_focus.txt`, фокусы `TT_war_border_depots` и `TT_war_red_army_salvage`:
  ```txt
  add_equipment_to_stockpile = { type = infantry_equipment_0 amount = 200 producer = TAN }
  add_equipment_to_stockpile = { type = support_equipment_1 amount = 20 producer = TAN }
  ```
  против старых фокусов (`TT_red_yurt`, `TT_soviet_advisors`, `TT_request_soviet_aid`): `type = infantry_equipment`.
- **Описание проблемы.** Внутри одного мода используются два разных имени одной «базовой винтовки». Как минимум одно из них не существует в БД техники HOI4 1.19.4, а `add_equipment_to_stockpile` по несуществующему типу **молча не выдаёт награду** и пишет `invalid database object` в error.log — ровно такой баг уже был пойман в 1.1.3 («вызывало ошибку `invalid database object for effect/trigger: tac_bomber_equipment`»). Тест «Reward effects use supported names» подтверждает лишь то, что автор *считает* эти имена поддерживаемыми; независимой сверки с БД движка нет, а прогон текущей версии в игре не выполнялся. Учитывая, что старые фокусы с `infantry_equipment` прошли несколько игровых версий (и автор вылавливал аналогичные ошибки глазами), более вероятно, что неверны именно новые `_0`/`_1`.
- **Impact.** Игрок военной ветки теряет 350 винтовок и 35 снаряжения «в никуда»; в error.log — постоянные ошибки при каждом прохождении ветки. Для мода, опубликованного в Steam Workshop (`remote_file_id=3827388899`), это массовый жалобный сценарий.
- **Решение (Before / After).**

  ```txt
  # Before (TT_war_border_depots)
  add_equipment_to_stockpile = { type = infantry_equipment_0 amount = 200 producer = TAN }
  add_equipment_to_stockpile = { type = support_equipment_1 amount = 20 producer = TAN }

  # After (после проверки в error.log; критерий — отсутствие invalid database object)
  add_equipment_to_stockpile = { type = infantry_equipment amount = 200 producer = TAN }
  add_equipment_to_stockpile = { type = support_equipment amount = 20 producer = TAN }
  ```
  и синхронно поправить ожидание теста (`assert.deepEqual(amounts, { infantry_equipment: 350, support_equipment: 35 })`). Если же в 1.19.4 действительно существуют `_0`/`_1` — тогда неправила *старая* часть мода и её надо править на новые имена; критерий один: свежий `error.log` после `add_equipment_to_stockpile` через консоль. До выяснения — блокировать релиз.

1. **Имена техники в БД HOI4 1.19.4** (`infantry_equipment_0`, `support_equipment_1`, `infantry_equipment`, `support_equipment`): файлы игры недоступны в песочнице; вывод сделан из внутренней противоречивости мода и прецедента 1.1.3. 5. **`on_daily_TAN`/`on_daily_SOV` (тег-суффикс on_actions)** — косвенно подтверждён поведением прошлых версий (ежедневный сброс рейда работал и был убран как избыточный), но прямого теста в 1.19.4 нет; стоит убедиться, что `error.log` не ругается на ключ.
6. **Семантика `removal_cost = -1`** для снятия духа игроком — не проверена; если движок трактует это как «снятие бесплатно», игрок сможет избавляться от штрафных послевоенных духов (например, `TT_postwar_military_base` с `political_power_factor = -0.10`). Проверить кнопку удаления духа в UI.
7. **Мультиплеер:** суперсобытие (`player_context`, `is_ai = no`), timed-флаги и `set_faction_rule` в MP не проверялись (никаких заявок в README нет — зафиксировать, что MP не поддерживается/не тестировался).
8. **WAV «IEEE float32 с fact chunk»** (`sound/tt_tuva/taishet_reveal.wav`) — воспроизведение на разных платформах/конфигурациях звука не подтверждено (docs сами просят проверить микшер).
9. **`set_faction_rule = war_declaration_rule_independent_countries_only`** — ID правила сверен с wiki, но не с игрой (README: «С установленной HOI4 1.19.4 здесь не сверено»); при неверном ID эффект молча не сработает.
10. **Не предоставлено для аудита:** реальный `error.log` после прогона, сейвы «до/после» тайшетского сценария, лаунчерский playset, версии DLC (By Blood Alone — ветка логики есть; остальные DLC не оговорены).

## Приложение 2: суперсобытие не отображалось — починка окна (2026-11-06)

**Симптом (сообщение пользователя):** окно суперсобытия «Тайшетский договор»
вообще не появлялось в игре, хотя флаг `TT_taishet_superevent_open`
выставлялся (тестовый `eval_effect`).

**Диагноз — `interface/tt_tuva_superevent.gui`, контейнер
`TT_taishet_superevent_window`: `position = { x = 0 y = -6000 }`.**
Окно в покое стояло на 6000 пикселей выше экрана. Поле `show_position`
не спасает при любом прочтении семантики анимации:
1. если анимация показа не запускается при переключении видимости
   scripted GUI (движок гарантирует её только для «штатных» окон) — окно
   навсегда остаётся на y=-6000;
2. если `show_position` — это «позиция ДО анимации» (комментарий грамматики
   cwtools `Config/interface/gui.cwt`: «Position before animation in pixels»),
   окно стартует в центре и за `animation_time = 0.6` уезжает в `position`
   (за экран);
3. работает только сценарий «анимация есть И ведёт к `show_position`» —
   именно он и не срабатывал.

Шаблон взят из `ECModder/2025-Dragon-Vs.-Eagle` `interface/DVE_superevent.gui`
(тот же `position = y:-6000` + slide); баг унаследован от шаблона. Рабочие
суперсобытия других модов (`klimPaskov/Chaos-Redux` `chaosx_super_events.gui`,
`EaW-Team/equestria_dev` state-lore popup) держат окно в `position = {0,0}`
без slide-полей и просто переключают видимость.

**Исправление (Before/After):**

```
- position = { x = 0 y = -6000 }        + position = { x = 0 y = 0 }
  show_position = { x = 0 y = 0 }         show_position = { x = 0 y = 0 }
  hide_position = { x = 0 y = -6000 }     hide_position = { x = 0 y = -6000 }
```

`position == show_position == {0,0}`: окно видимо при любом поведении
анимации; `hide_position = -6000` сохраняет «уезд» при закрытии. Ориентация
`orientation = center origo = center` — центр экрана.

Дополнительно кнопка закрытия: `quadTextureSprite` → `spriteType`
(поле для тайловых/угловых спрайтов; DVE-эталон кнопки использует
`spriteType`) и добавлен `clicksound = decisions_ui_button`
(проверенный ванильный звук, не зависит от пользовательского ассета).

**Верификация:** `tests/integrity.test.js` +2 проверки («окно в покое на
экране, `show_position` совпадает с `position`»; «`show_sound` разрешается в
`sound/*.asset`, кнопка по эталонному паттерну»). Оба набора зелёные
(28 + 14). Переделан helper `block()` — теперь реально вырезает комментарии.
В игре: пункт чек-листа «суперсобытие появляется в центре экрана».

**Слепое пятно:** запуск анимации показа для scripted GUI движком документами
не подтверждён (вики-зеркало `klimPaskov/Agentic-HOI4-Modding`
`hoi4_wiki/scripted_gui_modding.md`: `dirty` влияет только на `properties`,
видимость обновляется каждый тик — отсутствие `dirty` багом не является).
Проверка в живой игре обязательна.
